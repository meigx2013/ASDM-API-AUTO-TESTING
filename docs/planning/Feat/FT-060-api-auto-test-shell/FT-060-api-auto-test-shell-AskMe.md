# FT-060 接口自动化测试Shell脚本 — 需求访谈追问

> 本文档记录对 FT-060 接口自动化测试Shell脚本特性的逐问题追问，用于澄清需求模糊点后制定最终特性规格。

**创建日期**：2026-11-26
**状态**：已完成

---

## 背景摘要

### 核心价值

测试人员每天执行一次 Shell 脚本即可完成 `docs/api.json` 所描述的 ASDM Admin 全量接口自动化测试，自动完成鉴权、依赖编排、参数注入，并产出 Markdown 测试报告，替代手工逐接口调用。

### 数据源分析（docs/api.json）

| 维度 | 数据 |
|------|------|
| 业务域 | 12 个（认证授权/用户与组织/项目管理/工作空间/上下文库/流水线/资产注册/集成/代码评审/门户与内容/基础设施/数字分身） |
| 服务数 | 25 个（core=8880 … automation-adapter=8890） |
| 接口总数 | 1000 个 |
| 鉴权机制 | 5 种：`Authorization: Bearer {{token}}`（JWT，登录获取）、`asdmPat` 查询参数 / `X-Asdm-Pat` 头、`X-Internal-Token`、`X-Citic-Secret`、`X-Open-Access-Token` |
| BaseUrl 变量 | 13 个，默认本机端口，支持部署环境覆盖 |

### 用户明确的需求（已锁定）

| 编号 | 需求 |
|:----:|------|
| R1 | 测试人员每天执行一次脚本完成所有接口测试 |
| R2 | 接口参数维护机制：支持手工维护 + 执行时动态传参 |
| R3 | 按接口依赖关系编排执行顺序 |
| R4 | 执行时输出 LOG，便于跟踪进度 |
| R5 | 生成 Markdown 测试报告：每个接口的名称、方法、请求路径、状态、响应时间；失败接口重点标识并说明原因 |

### 变更范围

| 变更模块 | 变更内容 |
|----------|----------|
| `scripts/`（新增） | Shell 测试脚本主体（参数维护、依赖编排、执行引擎、日志、报告生成） |
| `config/`（新增） | 接口参数配置文件（测试人员手工维护的入口） |
| `reports/`（新增） | Markdown 测试报告输出目录 |
| `logs/`（新增） | 执行日志输出目录 |

### 决策点 2：测试覆盖范围

**问题**：每日执行是覆盖全部 1000 个接口，还是核心域子集？

**背景**：
- 全量 1000 接口含大量破坏性接口（删除、改密、停用）与外部适配接口（Citic、CodeArts、GitLab 等依赖外部系统真实凭据/连通性）。
- 参考同类实践（Ai-Fast/asdm-api-test 幂等体系）：全量 12 域每日跑约 40 分钟，其中大量接口因前置数据/外部依赖被 SKIP。
- 1000 接口中标注【推断】的请求/响应细节以实际服务返回为准，脚本需容忍响应结构差异。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | 全量 1000 接口，外部依赖接口失败/跳过如实入报告 | 覆盖最全，报告即接口资产台账 | 每日执行耗时长，外部依赖接口产生噪声 |
| B | 核心域优先（认证+用户组织+项目管理+工作空间等），其余域按开关启用 | 每日执行快、信号清晰 | 需维护启用开关 |
| C | 全量但分域开关，默认全开，可 `--domains` 过滤 | 兼顾 A/B，灵活 | 脚本稍复杂 |

**推荐**：✅ 选项 C — 全量分域开关 + `--domains` 过滤，默认全开。

**确认理由**：
1. 用户确认全量 1000 接口 + 域开关 + `--domains` 过滤，外部凭据缺失自动 SKIP。

**状态**：✅ 已确认（选项 C）

### 决策点 3：目标测试环境与默认 BaseUrl

**问题**：脚本默认指向哪个环境？

**背景**：
- api.json 变量默认本机端口（localhost:8880~8890）。
- 已知可用环境：DT01（https://asdm-dt01.leansoftx.com）、DT02、SIT。多服务端口映射在远程环境下通常收敛为同一网关域名。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | 默认 DT01（https://asdm-dt01.leansoftx.com），13 个 baseUrl 变量统一收敛到网关域名 | 贴近日常测试环境 | 需确认网关是否暴露全部 25 个服务 |
| B | 默认 localhost（与 api.json 一致） | 无网络依赖 | 本机未必部署全套服务 |
| C | 默认值放配置文件，运行时 `--base-url` / 环境变量覆盖 | 最灵活 | 无"开箱即默认" |

**推荐**：✅ 选项 C（配置文件默认 DT01，`--base-url` / 环境变量可覆盖）。

**确认理由**：
1. 用户选择：配置文件默认 SIT 环境（`https://asdm-sit.leansoftx.com/`），`--base-url` / 环境变量可覆盖。

**状态**：✅ 已确认（选项 C 变体：默认 SIT = https://asdm-sit.leansoftx.com/）

### 决策点 4：运行平台

**问题**：脚本在哪个 Shell 环境运行？

**背景**：
- 测试人员日常机器为 Windows（本机 Git Bash 路径 `D:\Program Files\Git\bin\bash.exe`，默认 `bash` 指向损坏的 WSL）。
- 依赖工具：curl（必选）、jq（JSON 提取）。Windows Git Bash 自带 curl，jq 需确认可用。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | 仅 Windows Git Bash | 贴合测试人员现状 | 无法在 Linux CI 复用 |
| B | Bash 脚本但严格 POSIX 兼容，Git Bash / Linux 均可运行 | 可复用于 CI | 编写约束略多 |
| C | PowerShell 为主 | Windows 原生 | 用户明确要求 shell 脚本，PowerShell 跨平台性差 |

**推荐**：✅ 选项 B — Bash 编写、避免 Bashism 过重，Git Bash 与 Linux 双兼容。

**确认理由**：
1. 用户确认 Git Bash/Linux 双兼容。

**状态**：✅ 已确认（选项 B）

### 决策点 5：参数维护机制形态

**问题**：R2 的"参数维护机制"以什么形式落地？

**背景**：
- 需要维护的参数类别：① 环境类（baseUrl ×13、各鉴权凭据 token/pat/internalToken/openAccessToken/citicSecret）；② 数据类（登录账号密码、各接口请求 body 中的业务参数如 projectId、workspaceId 等）。
- 1000 接口的请求体参数若全部硬编码在脚本中将不可维护。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | `config/env.sh` + `config/params.sh`（key=value，source 引入），CLI `--key=value` 覆盖 | 纯 shell、零依赖、测试人员易手工编辑 | 嵌套 JSON body 表达较弱 |
| B | `config/config.json` 单文件（jq 读取），CLI 覆盖 | 与 api.json 同构，body 可整段 JSON 维护 | 依赖 jq，手工编辑 JSON 易错 |
| C | 混合：env.sh（环境凭据）+ params.json（业务 body），CLI 覆盖 | 各取所长 | 两套维护入口 |

**推荐**：✅ 选项 C — 环境凭据用 env.sh（含脱敏注释），业务 body 用 params.json，CLI `--param key=value` 运行时覆盖，优先级：CLI > 环境变量 > 配置文件。

**确认理由**：
1. 用户确认混合方案：env.sh（环境凭据）+ params.json（业务参数）+ CLI 覆盖。

**状态**：✅ 已确认（选项 C）

### 决策点 6：依赖关系编排方式

**问题**：R3 的"按依赖关系编排执行顺序"如何表达？

**背景**：
- 天然依赖链：login → token → 其他 core 接口；创建类接口（创建项目/空间/用户）→ 其 id 供下游查询/更新/删除接口复用；PAT 创建 → integration 域接口。
- api.json 本身不含依赖信息（只是接口目录），依赖需要人工定义。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | 固定执行顺序清单（ordered pipeline：login → 建数据 → 各域 → 清理），依赖 id 通过变量捕获传递 | 直观、可控、实现简单 | 依赖信息分散在编排文件里 |
| B | 每个接口声明 `depends_on`，脚本做拓扑排序 | 依赖显式、可校验环 | 1000 接口逐个声明成本高 |
| C | 分层固定顺序（认证层→数据准备层→业务域层→清理层），域内按 api.json 目录序执行，域间用捕获变量衔接 | A 的简化版，规模可控 | 域内精细依赖不保证 |

**推荐**：✅ 选项 C — 分层编排 + 上下文变量捕获（`CAPTURED.projectId` 等），login 失败即中止。

**确认理由**：
1. 用户确认分层编排：登录鉴权层 → 数据准备层 → 业务域层 → 清理层，依赖 id 通过上下文变量捕获传递。

**状态**：✅ 已确认（选项 C）

### 决策点 7：断言策略

**问题**：接口"执行成功"的判定标准？

**背景**：
- api.json 部分响应为【推断】，字段级断言脆弱。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | 仅 HTTP 状态码（2xx/预期码） | 简单稳健 | 后端返回 200+业务错误会漏报 |
| B | 状态码 + 业务 code 字段（若响应含 code，校验其成功值） | 平衡 | 不同服务 code 约定不一 |
| C | 状态码 + 业务 code + 关键字段存在性（可按接口配置） | 最严格 | 维护成本高 |

**推荐**：✅ 选项 B — 状态码为主，响应含 `code` 时校验业务码（支持按接口配置预期值，默认容忍缺省）。

**确认理由**：
1. 用户确认状态码 + 业务码双校验，不做字段级断言（api.json 响应为【推断】，字段断言易误报）。

**状态**：✅ 已确认（选项 B）

### 决策点 8：破坏性/外部依赖接口处理

**问题**：删除、改密、停用等破坏性接口及外部依赖接口（Citic/GitLab/CodeArts）如何处理？

**背景**：
- 每日执行若真改密码/删数据会破坏环境。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | 破坏性接口默认 SKIP（报告标 SKIP 及原因），`--include-destructive` 显式启用 | 环境安全 | 覆盖不全 |
| B | 破坏性接口放在自建数据上执行（先创建后删除，闭环清理） | 覆盖全且安全 | 每个破坏接口需配套前置 |
| C | 全部真实执行 | 覆盖全 | 污染共享环境，风险大 |

**推荐**：✅ 选项 B 为主 + 外部凭据缺失的接口自动降级 SKIP（原因写入报告）。

**确认理由**：
1. 用户确认闭环执行 + 凭据缺失自动 SKIP。

**状态**：✅ 已确认（选项 B）

### 决策点 11：请求超时与响应时间口径

**问题**：单接口请求超时阈值设多少？响应时间如何统计？

**背景**：
- 1000 接口全量执行，个别慢接口不应阻塞整体进度。
- 报告需列出每个接口响应时间。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | curl `--max-time 30s` 默认，`--timeout` 可配；响应时间用 curl `time_total`；响应时间超过阈值（如 3s）标记 ⚠️ 慢接口告警 | 平衡 | 无 |
| B | 超时 60s，不设慢接口告警 | 宽松 | 慢接口不可见 |

**推荐**：✅ 选项 A。

**确认理由**：
1. 用户确认超时 30s（可配）+ 响应时间取 time_total + 超 3s 慢接口告警。

**状态**：✅ 已确认（选项 A）

### 决策点 12：JSON 解析工具依赖

**问题**：脚本解析 api.json / params.json / 响应体依赖 JSON 工具，如何选择与兜底？

**背景**：
- Windows Git Bash 默认不带 jq；本机已确认装有 node。
- 纯 sed/grep 解析 JSON 不可靠。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | 运行时探测：优先 jq，缺失则自动降级 node（`node -e` 封装成 `json_get` 函数） | 零安装成本，双环境可用 | 降级路径性能略慢 |
| B | 强制要求安装 jq，启动时检查缺失即报错退出 | 实现简单 | 测试人员需先装 jq |

**推荐**：✅ 选项 A — jq 优先、node 兜底，统一封装为 `json_get`/`json_query` 函数。

**确认理由**：
1. 用户确认 jq 优先、node 兜底的运行时探测方案。

**状态**：✅ 已确认（选项 A）

### 决策点 9：失败处理策略

**问题**：某接口失败后，脚本继续还是中止？

**背景**：
- R5 要求报告列出所有失败接口及原因，暗示继续执行。
- 但 login 等关键依赖失败时后续全部无意义。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | 关键链路失败即中止（login/token），普通接口失败继续 | 报告完整、不浪费执行 | 无 |
| B | 一律继续 | 最大化信息 | 依赖失败时下游大量误报 |
| C | 一律中止 | 快速失败 | 单点失败遮蔽其他问题 |

**推荐**：✅ 选项 A。

**确认理由**：
1. 用户确认：关键链路失败立即中止，普通接口失败继续执行并记录。

**状态**：✅ 已确认（选项 A）

### 决策点 10：报告与日志细节

**问题**：报告/日志的输出位置、命名与失败原因提取规则？

**背景**：
- R5 已定报告字段：接口名称、方法、请求路径、状态、响应时间；失败重点标识+原因。

**选项**：

| 选项 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A | `reports/api-test-report-YYYYMMDD-HHMMSS.md`（带汇总统计+失败明细），日志 `logs/run-同时间戳.log`，另保留最近 N 份自动清理 | 可追溯、不膨胀 | 无 |
| B | 固定文件名 `reports/latest.md` 覆盖写 | 简单 | 无历史 |
| C | 时间戳文件 + `latest.md` 软链/副本 | 兼顾 | 略复杂 |

**推荐**：✅ 选项 C — 时间戳报告 + latest 副本；失败原因 = HTTP 状态码非预期 / 业务码非预期 / 超时 / 连接失败 + 响应体摘要（截断至 200 字符）。

**确认理由**：
1. 用户确认时间戳报告 + latest 副本 + 保留最近 N 份 + 失败原因提取规则。

**状态**：✅ 已确认（选项 C）

### 关键技术决策汇总

1. 运行平台：Bash（POSIX 兼容），Git Bash / Linux 双兼容；JSON 解析 jq 优先、node 兜底（`json_get` 封装）。
2. 环境：配置默认 SIT（`https://asdm-sit.leansoftx.com/`），`--base-url` / 环境变量可覆盖。
3. 断言：HTTP 状态码 + 业务 code 双校验（可按接口配置预期值），不做字段级断言。
4. 破坏性接口：自建数据闭环（先创建后删除）；外部凭据（Citic/GitLab/CodeArts/OpenAccess/Internal）缺失自动 SKIP。
5. 超时：curl `--max-time 30s`（`--timeout` 可配），响应时间取 `time_total`。
6. 目录规划：`scripts/`（脚本主体）、`config/`（参数维护入口）、`reports/`（Markdown 报告）、`logs/`（执行日志）。
